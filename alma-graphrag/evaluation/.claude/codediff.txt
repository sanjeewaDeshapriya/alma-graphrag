Introduction — 1.5 pages\n\n### Page 1, column 1 — domain and problem\n- Travel is booked through ranked lists. The list decides which hotels a traveller considers at all [Ricci 2022; Ursu 2018].\n- Current platforms use two mechanisms:\n  - structured filtering, then a sort on one field (price or rating);\n  - more recently, text or embedding retrieval behind conversational assistants (RAG) [Lewis 2020; Gao 2023].\n- Case setting: Colombo, Sri Lanka. A dense city where congestion, processions and festivals change which hotels are practical. Tourism is a leading source of foreign exchange [SLTDA 2024].\n\n### Page 1, column 2 — four problems with existing hotel search\n- **P1. Distance is not reachability.** Platforms show straight-line distance to a centre; the traveller experiences travel time under traffic to *their* destination.\n- **P2. A static index cannot store a changing city.** \"Reachable in 5 minutes today\" is a relation between a hotel and current conditions. A flat attribute index or a text chunk has nowhere to put it.\n- **P3. One sort key cannot express a multi-criteria need.** \"Affordable, quick to reach, rated above 4.3\": a sort ignores two of the criteria, and a filter drops near-misses.\n- **P4. Who sets the criterion weights?** Hand-set weights are developer assumptions. Tuning them on the test set makes a system unfalsifiable. Eliciting them from people is principled but, as this paper shows, fragile.\n\n### Page 2, column 1 — research questions (state them explicitly)\n- **RQ1.** Does feasibility-first graph retrieval rank hotels better than filter-and-sort and modern text retrieval?\n- **RQ2.** Which part of the design carries the gain: the feasibility filter, the criteria, or the weights?\n- **RQ3.** Can criterion weights be identified from choices made in a realistic, sortable booking interface?\n- **RQ4.** Does the ranking agree with what real people booked, and can partly identified human weights still improve retrieval?\n\n### Page 2, column 2 — contributions (5, each tied to evidence)\n1. **Framework:** a feasibility-first retriever over a live property graph. Design Methodology — 4.25 pages\n\n### 3.1 Framework overview (1.0 p including Fig 2)\n- **Fig 2** (full width): `paper/ieee_conference_2026/figframework.png`.\n- Five layers:\n  1. data acquisition (hotel, rate, routing, traffic and event providers);\n  2. processing (canonicalise, deduplicate, price snapshot, geo-resolve);\n  3. storage (Neo4j property graph + pgvector text index built from the same 77 hotels);\n  4. online retrieval (intent → feasibility filter → scoring → explanation);\n  5. weight governance (study → estimator → acceptance gates → serving or research-only store).\n- Design principles to state:\n  - **Feasibility is decided before scoring.**\n  - **Unknown evidence fails a constraint.**\n  - **Scores are percentiles within the feasible pool.**\n  - **No generated query text reaches the database.**\n  - **A weight serves only if it passes all gates.**\n\n### 3.2 Problem formulation (0.4 p) — add this; Q1 reviewers expect it\n- Query q, city candidate set H. Intent ι(q) = (hard constraints C(q), preferences π(q)).\n- **Eq (1) feasible set:** F(q) = { h ∈ H : c(h) = true for all c ∈ C(q) }, where a constraint on an unknown value counts as false. If F(q) is empty, relax to H and flag the result.\n- **Eq (2) component:** x_k(h) = mid-rank percentile of h on criterion k within F(q), k ∈ {spatial, accessibility, facility, economic, disruption}; inverted for \"far\" or \"premium\".\n- **Eq (3) weights:** w(ι) = normalise(w₀ + Δ(ι)), with w₀ = (0.25, 0.20, 0.25, 0.15, 0.15).\n- **Eq (4) score:** S(h | q) = Σ_k w_k(ι) · x_k(h). Return the top k of F(q) with every x_k and w_k·x_k attached.\n- One sentence: the objective is feasibility-constrained ranking, not question answering.\n\n### 3.3 Data collection and datasets (1.0 p) — Table II\n**Hotel corpus (snapshot 15 Sep 2026)**\n- Providers, with a trust rule for each:\n  - Places provider: discovery, coordinates, text. Bootstrap resamples participants.\n- **Five gates.** A weight vector serves only if all pass for every criterion:\n  1. Discussion — 1.5 pages\n\n### 5.1 Why feasibility-first retrieval beats current practice (0.5 p)\n- **Missing information, not a poor sort.** Filter-and-sort scores 0 on travel-time queries because travel time under traffic is not in its index. The graph stores these relational, perishable facts on edges.\n- **Pruning before scoring.** A hotel that fails a hard need cannot be rescued by scoring well elsewhere. Treating unknown as failing avoids rewarding missing data. Ablation: worth 0.248 nDCG.\n- **Weight-insensitive by design.** Percentiles within the feasible pool, plus pruning, make any reasonable weighting beat the baseline (100% of 1,000). That makes deployment safer, because weights will be wrong in practice.\n- **Why text retrieval fails.** Embeddings and cross-encoders model topical similarity, not numeric constraint satisfaction (semantic vector 0.262, below the filter). This matches the finding that LLM agents break hard constraints [Xie 2024].\n- **Never worse.** 0 losses in 60 queries; exact ties on single-attribute needs. A platform can add the layer as a re-ranker without harming the queries it already handles well.\n- Explainability is a by-product: every result carries its component scores.\n\n### 5.2 Why the elicited weights failed, and what survived (0.5 p)\n- The interface, not the traveller, determined the fit. A sortable list of 32 made people screen the top 3 of a list sorted by a criterion being estimated. This is the consideration stage [Hauser \u0026 Wernerfelt 1990]; a compensatory logit models the choice stage.\n- The same position effect is causal in real hotel search [Ursu 2018]. Refining by sort is how travellers express preference [Chen \u0026 Yao 2017], and here the scenario-dependent sort choice (χ² = 320.5) is where the preference went.\n- A smooth position correction turned a null into apparent significance (χ² 121.4 vs 8.69). Only the placebo exposed it. **General lesson:** any weight learned from choices on a ranked list should face a position-only placebo.\n- What survived: price was the only criterion people could act on directly (a price sort existed). Scoping its weight to price-led intents is a principled use of partial identification: +13.1% where identified, no significant cost elsewhere.\n- Remedy (designed, not yet run): 5 alternatives per task, attributes visible, no sort control, randomised order, D-efficient blocked design (6 blocks; no dominated alternatives; maximum within-set attribute correlation 0.51) [Huber \u0026 Zwerina 1996].\n\n### 5.3 Threats to validity (0.4 p)\n- **T1, gold and filter share constraints (most important).** The rule gold grades the same hard constraints the proposed filter enforces. Discussion — 1.5 pages"," ","-### 5.1 Why the framework beats current practice (0.5 p)","-- Current practice fails on accessibility and disruption because the needed information is **absent from its index**, not because its sort is poor.","-- Travel time and event exposure are **relational and perishable**, so they belong on graph edges.","-- Pruning on feasibility first removes hotels no weighting could rescue: the ablation shows it is worth 0.248 nDCG.","-- Robustness: 100% of random weightings beat the baseline. no generated query text ever reaches the database.\n- This gives both safety (no injection) and reproducibility (intents are frozen for evaluation).\n\n**Step 2 — feasibility filter**\n- Prune every candidate that fails a hard constraint.\n- An *unknown* value for a constrained attribute also fails, because feasibility requires positive evidence.\n- If nothing survives, relax the filter and flag it.\n\n**Step 3 — scoring** — Equation (1):\n\u003e S(h) = w_s·s(h) + w_a·a(h) + w_f·f(h) + w_e·e(h) + w_d·d(h), with Σw = 1\n\n| Component | Definition |\n|---|---|\n| s — spatial | percentile rank of distance to the request\u0027s anchor (inverted for \"far from the crowds\") |\n| a — accessibility | percentile rank of traffic-aware travel time |\n| f — facility | 0.40·amenity match + 0.20·attraction match + 0.20·pct(rating) + 0.20·pct(star) |\n| e — economic | percentile rank of price (inverted for \"premium\") |\n| d — disruption | 1 − exposure; own signals if present, otherwise neighbour state (hop decay 0.5, max 2 hops) |\n\n- **Why percentiles:** computed within the surviving pool, so a weight means the same thing at elicitation and at serving time.\n- **Intent adjustment** before normalisation (Table IV):\n  - cheapest → economic +0.20\n  - highest-rated → facility +0.20\n  - most-accessible → accessibility +0.20, disruption +0.10\n  - avoid traffic → disruption +0.15, accessibility +0.05\n  - far → disruption +0.10, spatial −0.10\n  - amenities → facility +0.10\n- **Hand-set prior:** spatial 0.25 · accessibility 0.20 · facility 0.25 · economic 0.15 · disruption 0.15.\n- **Explainability:** every ranked hotel carries its component scores and weighted contributions.\n\n### 3.5 Human weight elicitation and acceptance gates (0.6 p)\n- Conditional logit over the 5 components, fitted per display condition and macro-averaged; clustered bootstrap by participant.\n- **Five acceptance gates** — a weight may serve only if all pass:\n  1. **G1 placebo:** beat the estimator run on position-only synthetic data.\n  2. **G2 likelihood ratio:** components improve on a position-only model.\n  3. **G3 interval:** participant-clustered CI excludes zero.\n  4. **G4 held-out:** improves held-out log-likelihood.\n  5. **G5 stability:** signs stable across leave-one-task-out refits.\n- Why G1 matters: the estimator clips negatives and projects onto a simplex, so it returns plausible weights even from pure noise.\n- **Scoped application:** use the elicited vector only for intents where the study could isolate that attribute (price-led: budget, cheap/premium, cheapest sort); otherwise the prior.\n\n### 3.6 Evaluation design and metrics (0.8 p, including Fig 4)\n- **Fig 4** = `figevaluation.png` (one column): two routes, never pooled.\n- **Route 1 — graded relevance:**\n  - Grade 2 = satisfies the request; 1 = within tolerance; 0 = fails.\n  - Tolerance bands: price ±15%, rating 0.2, one star, travel time +2 min, delay +3 min.\n  - The bands are implemented by **no** compared system, which is what removes circularity.\n  - Price-slice cut points are absolute LKR values frozen in the query file, not pool percentiles (which would be circular).\n- **Route 2 — booking choices:**\n  - Per choice: relevant = the one hotel booked.\n  - Per task: relevant = hotels chosen by ≥ 2 held-out people; Discussion — 1.5 pages\n\n### 5.1 Why the framework beats current practice (0.5 p)\n- Current practice fails on accessibility and disruption because the needed information is **absent from its index**, not because its sort is poor.\n- Travel time and event exposure are **relational and perishable**, so they belong on graph edges.\n- Pruning on feasibility first removes hotels no weighting could rescue: the ablation shows it is worth 0.248 nDCG.\n- Robustness: 100% of random weightings beat the baseline. The contribution is the architecture, and it is insensitive to exact weights — good for deployment.\n- Explainability comes as a by-product: per-criterion decomposition on every result.\n\n### 5.2 Why the elicited weights mostly failed — and what survived (0.5 p)\n- A realistic, sortable 32-hotel list cost identification: people chose the top 3 of a list they had sorted by an attribute under estimation.\n- Cite Ursu (2018): the same position effect in real hotel search.\n- A smooth log-rank correction turned a confound into an apparently significant result; only the placebo exposed it.\n- **What survived:** price was sortable, so price preference was expressed in a way the model could read. Scoping it to price intents gives +13.1% on price queries, statistically tied elsewhere.\n- **General lesson:** identify which attributes the interface let respondents act on independently, and scope elicited weights to those conditions.\n\n### 5.3 Threats to validity (0.4 p)\n- Route 1 labels are author-derived rules. Mitigations: tolerance bands no system implements; sensitivity sweep (proposed wins at all 6 band scales); Route 2 as an independent ground truth.\n- LLM pre-label pilot: model vs rule labels agree **51.6% exactly, 64.1% binary** — shows the room for disagreement; independent annotation is the next step [Thomas et al. 2024].\n- One city, 77 hotels: generalisation is untested.\n- The ablation and disruption results come from the 58-hotel snapshot.\n- The live snapshot has little real congestion (maximum observed delay 0.2 min), so disruption is shown under controlled scenarios.\n- The scoped-weight rule is a declared design decision.\n\n### 5.4 Practical implications (0.1 p)\n- It deploys as a re-ranking layer over existing inventory, with no search-stack replacement.\n- Useful to destination-management and business-travel settings during events and closures.\n\n---\n\n## 6.
